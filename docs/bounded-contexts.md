# 境界づけられたコンテキスト

**境界づけられたコンテキスト**は、あるモデルが通用する範囲の境界。
同じ言葉でも文脈が違えば別のモデルになる、という考え方に基づく。

---

## 結論

このアプリケーションは**実質的に単一のコンテキスト**（タスク管理）で構成されている。
分割する理由が現時点では存在しない。

ただし **完了履歴は、将来コンテキストとして分かれ得る場所**として認識しておく。
以下はその分析。

---

## 同じ「Task」が2つの意味を持ち始めている

T5-2 で完了履歴を導入したとき、保存先をタスク本体とは別のキーにした。
「関心事が違うものを同じ入れ物に入れると、片方の都合がもう片方を縛る」ためだが、
これはコンテキスト分離の芽でもある。

両者にとっての「Task」を並べると、意味が違っている。

| | タスク管理から見た Task | 完了履歴から見た Task |
|---|---|---|
| 性質 | 生きているもの | 起きたことの記録 |
| 名前 | 変わる（`rename`） | **完了した時点で固定** |
| 完了状態 | 行き来する | 常に「完了した」 |
| 同一性 | `TaskId` | その完了という出来事そのもの |
| 削除 | できる | 消してはならない（記録だから） |
| 関心 | 今やるべきことは何か | 何をやってきたか |

**同じ Task という言葉が、既に2つのモデルを指している。**
タスク管理では「名前は変わるもの」だが、完了履歴では「名前は変わらないもの」。
この食い違いこそが、コンテキストを分ける動機になる。

---

## それでも今は分けない理由

### 1. 食い違いがまだ痛くない

現在 `TaskCompleted` は完了時点の `TaskName` を抱えて運ぶため、後から名前を
変えても履歴は変わらない。**イベントがイミュータブルであることで、
食い違いは既に解消されている。** 追加の仕組みを要していない。

### 2. 履歴側に固有のルールがない

完了履歴がやっているのは「記録する」「新しい順に返す」だけで、
独自の不変条件も計算もない。モデルと呼べるほどの中身がないものに
境界を引いても、フォルダが増えるだけになる。

### 3. 語彙を共有できている

完了履歴は `TaskName` をそのまま使っている。これは**共有カーネル**
（2つのコンテキストが一部のモデルを共有する関係）にあたる。
共有する範囲が `TaskName` と `TaskCompleted` だけで安定している限り、
この関係は維持コストが低い。

---

## 現在の関係

```
  タスク管理                     完了履歴
  ┌──────────────┐  TaskCompleted  ┌──────────────────┐
  │ Task         │ ──────────────▶ │ CompletionHistory │
  │ TaskList     │    （イベント）  │                  │
  │ TaskName ────┼─────────────────┼──▶ 共有して使用   │
  └──────────────┘                 └──────────────────┘
       上流                             下流
```

- **上流・下流の関係**: タスク管理で起きたことが履歴に流れる。逆向きはない
- **結合はイベント1種類のみ**: 履歴は `TaskList` も `TaskRepository` も知らない
- **共有カーネル**: `TaskName` を共有している

この一方向性のおかげで、分割が必要になったときの作業は小さい。

---

## どうなったら分けるべきか

### 1. 履歴側に固有のルールが育つ

「週ごとの完了数」「連続達成日数」「一度も完了していないタスクの警告」などを
扱い始めると、履歴は独自のモデルを持つ。そのとき `TaskName` を借り続けると、
**タスク管理側の都合（最大100文字、改行不可）が履歴の制約になる**。
記録として保存済みの名前に、後から変わった制約を適用できない矛盾も起きる。

→ 履歴側に自前の値オブジェクト（例: `CompletedTaskName`）を持たせ、
　イベントを受け取る時点で変換する（腐敗防止層）。

### 2. 用語が衝突する

履歴側で「Task」が「完了記録」を指すようになり、会話で
「Task を消して」が両者で違う意味になったとき。
**言葉が衝突したら、それは境界が必要になった合図。**

### 3. 保存先やリリースの単位が分かれる

履歴だけをサーバーに置く、履歴だけ別のリリースサイクルで更新する、
別の担当者が持つ、といった状況。技術的・組織的な境界は
そのままコンテキストの境界になりやすい。

### 4. 件数の要求が変わる

タスクは数十件でも、履歴は数万件になり得る。集約の粒度もリポジトリの
設計も変わるため、同じモデルで扱い続けるのが無理になる。

---

## 将来ありそうな他のコンテキスト

| コンテキスト | そこでの「Task」 | 分かれる理由 |
|---|---|---|
| 通知 | 通知を送る対象。締切と宛先を持つ | 送信の成否やリトライという別の関心事 |
| 共有・コラボレーション | 割り当て先と権限を持つもの | 誰が何をできるかという別のルール |
| 統計・分析 | 集計対象の数値 | 個々の同一性より集合の傾向が関心事 |

いずれも「Task」という語は共通だが、**持つべき属性も守るべきルールも違う**。
1つのモデルにすべてを詰め込むと、どの文脈にも合わない中途半端なものになる。

---

## この分析から得られること

境界づけられたコンテキストは、大規模なシステムだけの話ではない。
**このアプリの規模でも「同じ言葉が2つの意味を持ち始める」現象は既に起きている。**

重要なのは、分けることではなく **境界の候補に気づいていること**。
気づいていれば、痛みが出たときに「ここを分ければいい」と判断できる。
気づかないまま1つのモデルに詰め込み続けると、どの文脈にも合わないモデルが
できあがり、そこから戻すのは非常に高くつく。
