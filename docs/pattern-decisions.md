# 採用しなかったパターンと、必要になる条件

DDD のパターンは問題に対する解であって、適用すること自体が目的ではない。
ここには「今は採用しない」と判断したパターンについて、**なぜ今は不要か**と
**どうなったら必要になるか**を残す。将来この判断を見直すときの材料になる。

---

## ドメインサービス

### どういうものか

どのエンティティにも値オブジェクトにも自然に属さない操作を置く場所。
典型例は口座間の送金で、送金元・送金先どちらの口座のメソッドにするのも
不自然なため、両方を引数に取るサービスに置く。

### 今は採用しない理由

現在の操作はすべて、持ち主がはっきりしている。

| 操作 | 持ち主 | なぜそこか |
|---|---|---|
| 名前の妥当性検査 | `TaskName` | その値自身の不変条件 |
| 完了・未完了 | `Task` | その Task 自身の状態 |
| 重複の排除・並び順 | `TaskList` | 集合でなければ判断できない |
| 表示対象の選択 | `TaskFilter` | 条件そのもの |
| 未完了の件数 | `TaskList` | 集合の性質 |

宙に浮いている操作がない以上、サービスを置く必要がない。
**ドメインサービスを早く作りすぎると、本来エンティティに属する振る舞いの
逃げ場になり、ドメインモデル貧血症を招く。**

### どうなったら必要になるか

いずれも「**2つ以上の集約やエンティティに等しく関わり、どれかに置くと不自然**」
という形をしている。

1. **複数のタスクリストを統合する**
   個人用と共有用のリストをマージする機能。`listA.merge(listB)` と
   `listB.merge(listA)` のどちらが自然かを決められない。
   → `TaskListMerger` のようなサービスが要る。

2. **似ているタスクの検出**
   「Eat lunch」と「lunch」を重複候補として提示する機能。文字列の類似度計算は
   `Task` の責務ではなく、`TaskList` の責務でもない。
   → `SimilarTaskDetector` のようなサービスが要る。

3. **別のユーザーへタスクを移譲する**
   移譲元と移譲先という2つの集約にまたがる操作。どちらの集約にも
   相手を変更する権限を持たせたくない。
   → 移譲を担うサービスが要る。

### 判断の順序

サービスを作る前に、必ずこの順で問い直す。

1. この操作は、ある値そのものの性質ではないか（→ 値オブジェクトへ）
2. ある Task 自身の状態変化ではないか（→ エンティティへ）
3. 集合として初めて判断できることではないか（→ 集約ルートへ）
4. 上のどれでもなく、複数のものに等しく関わるか（→ ドメインサービス）

## 仕様パターン (Specification)

### どういうものか

選択条件をオブジェクトとして表現し、`and` / `or` / `not` で合成できるようにする。

```ts
const target = activeTasks.and(dueThisWeek).and(taggedWith("work"));
tasks.filter(target);
```

### 今は採用しない理由

`TaskFilter` は All / Active / Completed の3つに固定されており、
**合成する必要が一度もない**。仕様パターンにすると、条件クラス3つに加えて
`AndSpecification` などの合成器とそのテストが増えるが、得られるのは
「将来使うかもしれない柔軟性」だけになる。

T1-6 で列挙的な値オブジェクトを選んだのは、取り得る値が3つに限られることを
型とインスタンスの両方で保証できるため。合成できないことは、この設計では
欠点ではなく制約として機能している。

### どうなったら必要になるか

1. **ユーザーが条件を組み合わせられる検索**
   「未完了 かつ 今週締切 かつ タグが work」のように、実行時に条件が決まる。
   固定の列挙では表現できない。

2. **同じ条件を複数の文脈で使い回す**
   「通知の対象」という条件を、一覧の絞り込みにも、通知送信の判定にも、
   保存時の検証にも使う。条件がひとつの場所にないと定義がずれる。

3. **条件を保存して再利用する**
   ユーザーが作った絞り込み条件に名前を付けて保存する。
   条件がデータとして永続化できる形である必要がある。

### 移行はいつでもできる

`TaskFilter` は既に `matches(task: Task): boolean` を持っており、
仕様パターンの核心部分は満たしている。必要になったら次の順で移せる。

1. `TaskSpecification` インターフェース（`matches` だけを持つ）を抽出する
2. `TaskFilter` の3つをその実装にする
3. `and` / `or` / `not` の合成器を追加する

**今やらない判断のコストは低い。** 逆に今やってしまうと、使われない合成器を
抱えたまま維持することになる。

## この文書の使い方

上に挙げた「必要になる条件」に当てはまる要件が出てきたら、その時点で
改めて検討する。要件がないうちにパターンを入れるのは、問題がないところに
解を置く行為であり、コードを読む人に「なぜこれがあるのか」という
無駄な問いを残すことになる。
